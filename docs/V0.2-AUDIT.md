# v0.2 audit and implementation order

## Current baseline

The existing product is a dependency-free Node.js prototype. `src/core.js` generates eight seeded bass, chords and melody ideas and serializes MIDI type 1. `src/schema.js` validates provider output; `src/operations.js` connects offline, HTTP and CLI providers. `src/server.js` serves a loopback UI and JSON API, while `src/mcp-server.js` exposes a line-oriented stdio JSON-RPC server. `web/app.js` provides a basic piano roll and Web Audio preview. None is a native plugin.

## Findings

- Fixed: provider HTTP failure bodies and CLI stderr were returned to HTTP/MCP clients and could disclose private upstream data. Errors now include the provider and status or exit code, without upstream text.
- Fixed: rounding could place a validated note at the end of the pattern or beyond it. Timing is now normalized in integer thousandths of a beat and bounded after rounding.
- High: successful provider responses are buffered without a size limit before validation; fetch has a timeout but no caller-driven cancellation or retry policy.
- High: CLI child termination and Windows shell execution need cross-platform process-tree, argument handling, timeout and failure tests. CLI output formats and authenticated operations have not been verified live.
- High: MCP stdin and messages lack explicit size bounds, and protocol interoperability beyond the existing tests has not been established.
- High: there is no native audio thread, host synchronization, plugin state, JUCE project or DAW integration. A successful build will not prove host compatibility.
- Medium: MIDI export has structural tests but no independent parser round-trip suite. Overlapping equal pitches and host transport discontinuities need explicit behavioral definitions.
- Medium: HTTP binds to loopback and checks Host, Origin for POSTs, and JSON content type; these protections and oversized requests need adversarial integration tests. Provider status checks synchronously launch CLI discovery.
- Medium: only OpenAI's success format has a mocked provider test; Anthropic, OpenRouter, Ollama, failed bodies, malformed outputs and partial responses need additional coverage. Live AI service access requires appropriate user configuration.
- Medium: UI currently has basic note editing and preview, not multitrack editing, undo, velocity editing, drag to DAW or the requested professional workflow. Live browser audio and DAW validation remain outstanding.

## Ordered milestones

1. Bound provider and MCP input/output, sanitize failures, test timeouts and subprocess behavior without credentials. Add adversarial HTTP, CLI and provider tests and an independent MIDI round-trip test.
2. Define versioned composition and provider contracts, then write an RFC for native transport and state. Preserve the offline generator and validate all data crossing process boundaries.
3. Add pinned JUCE and CMake targets for VST3 and Standalone. Move generation and AI work off the audio thread; transfer only bounded, prevalidated events to real-time processing. Implement transport discontinuities, note-off handling and state serialization with dedicated tests.
4. Build on Windows in CI and upload unsigned test artifacts; verify in REAPER before making host compatibility claims. Extend to other hosts only after actual tests.
5. Build the requested editing, preset and AI functionality incrementally on the verified core.

## Current environment and limitations

Node 24 and a C++ compiler are available. CMake and several Linux JUCE development libraries are absent. JUCE's Git repository is reachable, but the GitHub API returned `Forbidden` and the GitHub CLI reported invalid authentication, so CI dispatch, artifact collection and PR creation were not verified. A Windows build or host test was not performed. Resolve build prerequisites and GitHub API access before claiming this milestone complete.
